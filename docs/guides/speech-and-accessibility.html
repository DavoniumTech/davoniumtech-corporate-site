Home / Documentation / Speech and accessibility

DVNM Bot guide · Updated 21 October 2026

Voice that stays optional—and answers that stay available.

DVNM Bot uses speech synthesis built into the visitor’s browser or operating system. That keeps the feature lightweight, but each device may provide different voices and capabilities.

1. How spoken output works

The visitor selects a curated topic, reads the written answer, and presses Hear this answer. The browser then asks its speech engine to read the visible answer. No audio starts automatically, and the current guide does not send the answer to an external speech provider.

The robot’s mouth animation responds to speech activity events. It is a visual cue, not phoneme-perfect lip synchronisation. Text, links, and the Stop voice button remain usable if speech is unavailable.

2. Why voices differ

Voice availability depends on the browser, installed system voices, language settings, network access for online voices, device accessibility settings, and whether the browser allows speech output in the current context. Some mobile browsers return their voice list later than desktop browsers; others may stop speech when audio focus changes or a tab loses activity.

3. Troubleshooting interrupted speech

  1. Tap the voice button once and give the device a moment to start. Repeated rapid taps can cancel the current utterance.
  2. Check that the phone’s media volume is up and that silent mode, Bluetooth routing, or another audio session is not redirecting sound.
  3. Verify that the browser and operating system have a speech voice/language installed and enabled. Try the device’s built-in text-to-speech or accessibility settings.
  4. Reload the page once if the browser speech engine becomes stuck, then select the topic and try again.
  5. Try an up-to-date browser over HTTPS. Embedded or restricted web views may not expose the same speech features as a normal browser.
  6. If it still fails, read the on-screen answer and follow its link. The site must not block navigation because speech failed.

4. What helpful error handling looks like

An interrupted or cancelled utterance should not be reported as a permanent device failure. The site should distinguish a user stopping speech from unsupported speech and genuine synthesis failures, re-enable the button after errors, and preserve the written response.

Starting a new utterance should avoid cancelling an idle speech engine immediately before speaking. When a selected voice fails, a site may retry with the default device voice once rather than looping endlessly. A retry is not a guarantee: operating-system and browser restrictions remain outside the website’s control.

5. Accessibility and privacy boundaries

  • Never autoplay speech without consent.
  • Keep written answers and links available to deaf/hard-of-hearing visitors and anyone on a muted device.
  • Provide a clear stop control and status message.
  • Respect reduced-motion settings and keep animations decorative.
  • Do not imply a robot is a generative AI agent when it uses curated answers.
  • Do not collect private user speech or record a visitor’s microphone for this feature.

6. Known limits

Browser speech synthesis is not a managed voice service. Davonium Technologies cannot promise a particular voice, identical pronunciation, offline output, or exactly the same startup time on every device. A future hosted voice system would require separate cost, privacy, consent, availability, and security decisions.
