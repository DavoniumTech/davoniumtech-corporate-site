Web app engineering principles

The engineering choices behind our lightweight public website and how we verify behaviour rather than trusting appearance alone.

Simple architecture

We use HTML for structure, CSS for presentation, and vanilla JavaScript for interaction where that keeps the solution maintainable. Our public company site does not need a client framework or package build to render its core pages.

We choose added complexity only when the user’s needs justify it and the long-term maintenance cost is understood.

  • We separate shared styling from page content.
  • We keep important navigation and documentation links in HTML.

Progressive enhancement

We treat browser APIs as optional enhancements. If installation, IntersectionObserver, local storage, or a theme media query is unavailable, the core page remains readable and has a reasonable fallback.

We keep the system theme as the default and remember a manual choice only after a visitor makes one.

  • We use feature detection and safe storage access.
  • We respect reduced-motion preferences and low-power signals.

Reliability and errors

We test the real result of a click, route, form, or installation action. We distinguish browser-managed results from things our code controls.

The contact form creates an email handoff, not a database record. The install button can call a native prompt only when the browser provides one.

  • We provide explicit error and recovery states.
  • We use real HTTP routes and a custom 404 page rather than making every unknown route look successful.

Verification and maintenance

We run syntax, link, metadata, and manifest checks before a release and then review the actual hosted version on phone and desktop devices.

Static checks catch many file and syntax issues, but they do not replace real-device testing or hosting-log review.

  • We examine offline caching after a successful first visit.
  • We retain a known-good source revision before high-impact changes.

How we evaluate the result

We check required user paths, error handling, responsive behaviour, and maintenance cost before treating an implementation as ready.
