Accessibility checklist

How we design and check the site so people can navigate it with different devices, input methods, and access needs.

Why accessibility matters

We want visitors to understand our products and use our website without being blocked by a particular device, pointer, or sensory preference. We build on semantic HTML so browsers and assistive technology can identify headings, links, buttons, forms, and navigation landmarks.

Accessibility is part of how we evaluate a useful experience, not a visual layer added at the end.

  • We keep page titles, heading order, labels, and link names meaningful.
  • We make primary actions available through ordinary links and buttons.

Our design choices

We use readable line lengths, responsive layouts, visible focus states, and contrast-aware colours. Our theme follows the visitor’s operating-system preference unless they intentionally choose a different appearance.

Animation is decorative. It never carries information that a visitor cannot access without motion.

  • We respect the reduced-motion setting and avoid making content depend on animation.
  • We keep forms, menus, dialogs, and theme controls labelled and operable by keyboard.

How we check the experience

When we change navigation, forms, themes, product cards, or install interactions, we check the common path as well as the recovery path. Automated tools help us find issues, but they do not replace manual keyboard and zoom testing.

We keep essential content in the page markup rather than making it appear only after a hover or a click.

  • We test narrow phone widths, keyboard focus, Escape-to-close behaviour, and readable zoom.
  • We check that reveal animations do not hide content when motion is reduced or an observer is unavailable.

Scope and continued improvement

Accessibility is an ongoing quality goal. A successful automated scan is not proof that every person or assistive technology will have the same experience.

We use visitor reports and reproducible examples to identify the next improvement, and we describe known limitations rather than claiming perfect accessibility.

  • We prioritise barriers that stop people completing a task.
  • We revisit affected interactions when browser support or the interface changes.

Testing an interface change

When we change a component, we check it with keyboard navigation, focus visibility, zoom, and a narrow-screen layout before relying on appearance alone.
