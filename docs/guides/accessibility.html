Accessibility checklist

Practical design and implementation checks for keyboard and assistive-technology users.

Purpose. Practical design and implementation checks for keyboard and assistive-technology users. Use this guide as practical information and verify details against the deployed product and any applicable agreement.

Overview and purpose

Semantic HTML gives browsers and assistive technologies a meaningful structure. Pages need descriptive titles, logical headings, navigation landmarks, labelled inputs, and native buttons or links for their intended actions.

For this area, the team should make the intended behaviour explicit, keep the implementation proportionate to the need, and record any constraint that could affect a user. Where a service relies on a browser feature or external provider, describe that dependency instead of implying universal support.

  • Identify the person, task, and expected result relevant to accessibility checklist.
  • State requirements and limitations in language a non-specialist can follow.
  • Test the common path, an error path, and the recovery route before release.

Decisions and requirements

Colour should not be the only way to communicate meaning. Text and controls need adequate contrast, focus outlines must remain visible, and layouts should work at narrow widths and zoomed sizes.

Practical implementation

Honour reduced-motion preferences and make sure essential information does not depend on an animation. Menus and dialogs need keyboard access, a predictable close path, and focus behaviour that supports visitors.

Validation and maintenance

Automated audits can find common issues, but manual keyboard testing and assistive-technology checks remain useful. Re-test accessibility after changes to navigation, themes, forms, or modal interactions.
