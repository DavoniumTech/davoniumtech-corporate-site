Project delivery process

How we move a website or product task from a clear request to an implementation that can be reviewed and maintained.

Understand the request

We start by identifying the audience, the task they need to complete, the existing system, and the outcome that would count as success. That keeps the work anchored to a real need instead of a list of decorative features.

We confirm scope and constraints before making architectural decisions that affect cost, privacy, or future maintenance.

  • We list required pages, flows, devices, integrations, and content.
  • We separate confirmed requirements from assumptions and open questions.

Build in reviewable changes

We keep source files organised and commit meaningful changes so a reviewer can see what changed and why. For static sites, we prefer simple files and minimal dependencies when they solve the requirement.

A change is not complete because it compiles; user-facing behaviour and failure paths need verification too.

  • We preserve existing working functionality while changing the smallest relevant area.
  • We review mobile layout, keyboard behaviour, navigation, and status messaging.

Verify before publishing

We test direct page routes, links, forms, responsive layouts, metadata, and the hosting preview. For PWAs, we also check installation eligibility and offline recovery after resources are cached.

We keep environment-dependent behaviour clear, especially where a browser or third-party provider controls the result.

  • We investigate build logs when deployment fails.
  • We distinguish a Git push from a successful production release.

Release and maintain

We publish through the configured hosting branch or workflow and keep a known-good commit for recovery. We update product status and public documentation alongside changes that affect visitors.

The delivery scope determines ongoing maintenance; we do not imply round-the-clock monitoring or support unless it is explicitly included.

  • We record known limitations and a practical recovery route.
  • We review feedback to decide what needs fixing next.

A release we can verify

We split work into reviewable changes, test the affected experience, and retain a recovery path before publishing to the production branch.
