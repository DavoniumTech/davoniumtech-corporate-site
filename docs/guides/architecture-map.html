Website architecture and file map

A practical map of the pages, assets, scripts, offline behaviour, and discovery files that make up this website.

Page and route structure

We publish our website as individual HTML pages rather than a single-page JavaScript application. The homepage, product pages, services, work, contact, install page, support page, and documentation can be requested directly.

Cloudflare Workers Static Assets uses clean routes for HTML pages. We link to /products, not products.html, and to /docs/ for the documentation landing page.

  • index.html is the root homepage; top-level pages have matching .html source files.
  • Public guides live in docs/guides/ and keep separate titles, canonical URLs, and content.

Styles and behaviour

Shared styles live in assets/css/styles.css. The vanilla JavaScript in assets/js/site.js handles theme preference, mobile navigation, install guidance, documentation filtering, the contact email handoff, and limited scroll reveals.

The navigation and guide links remain ordinary HTML anchors, so our website remains understandable and navigable without the search filter running.

  • CSS and JavaScript are shared to avoid duplicating interaction logic on every page.
  • Images include intrinsic dimensions and deferred loading where appropriate.

PWA and offline files

manifest.webmanifest declares the app name, launch URL, display mode, and icon variants. sw.js caches the essential shell and stores pages as they are successfully visited.

Our PWA runs our website in an installable browser window; it is not a native Android package or a promise that every route works on the first offline visit.

  • Rounded and maskable icon files support different home-screen icon treatments.
  • The offline page explains the state when a requested resource is not already available locally.

Discovery and deployment

We maintain robots.txt, sitemap.xml, llms.txt, and llms-full.txt to describe public routes and help crawlers find the content. wrangler.jsonc configures the static asset directory and HTML route handling.

The branch we configure Cloudflare to deploy determines what people see. A successful Git push does not by itself prove that the production deployment completed.

  • We check clean routes, direct reloads, and the canonical domain after deployment.
  • We keep build notes and internal deployment instructions in the source repository, not in the public page navigation.

Finding the right source file

We use the HTML page as the source for content and metadata, shared CSS for visual rules, shared JavaScript for optional interactions, and the service worker for offline caching. We update this map when the shipped structure changes.
